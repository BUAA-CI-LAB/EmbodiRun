# 手动控制

Control 服务统一处理模型动作和键盘、手柄输入。任务运行时提交模型生成的动作块；
手动输入先在 CPU 上转换为操作指令，再由服务端仲裁线程映射为具体的机器人动作。

支持的 HTTP 控制路由：

- `GET /v1/control` 返回运行时权限、活动任务状态以及
  `last_error`。
- `POST /v1/control/emergency-stop` 在模型
  队列之外锁存急停。
- `POST /v1/control/reset` 清除软件急停锁存。
- `POST /v1/control/manual/acquire` 授予手动控制所有权。
- `POST /v1/control/manual/release` 将所有权交还给模型控制。
- `POST /v1/control/manual/deadman` 接受 `{"active": true}` 或
  `{"active": false}`。
- `POST /v1/control/manual/action` 接受包含
  `values` 和 `metadata` 的 `RobotAction` JSON 对象；异步动作提交返回 ticket 状态。

## 连接键盘与手柄

启动 HTTP 遥操作客户端后，键盘控制始终可用：
`python -m embodirun.services.control.teleop --endpoint http://127.0.0.1:8100`。
添加 `--joystick /dev/input/js0` 可启用手柄，同时必须用
`--robot-kind arx5` 或 `--robot-kind so101` 选择机器人对应的摇杆轴映射。
不使用手柄时，只提供键盘急停、重置和退出操作。

输入轮询不等待机器人观测。摇杆输入先转换为 CPU 操作指令，
再由服务端的机器人命令线程完成动作映射。HTTP 状态查询和动作提交仍可能等待本机 I/O，
不提供硬实时保证。ARX5 映射已通过软件测试；实际使用前仍需核对手柄映射。

## 手动接管与任务切换

每个服务拥有一个已配置的机器人和一个仲裁器；停止一个机器人不会
停止其他服务。模型动作使用有界 FIFO。手动动作有
一个待处理槽位，新输入会覆盖尚未执行的旧输入。获取手动控制会取消模型任务，
包括接管之后到达的推理结果。释放手动控制
允许新的模型任务，但绝不会恢复已取消的任务。

急停不经过动作队列：触发后会锁定停止状态、取消当前任务，并清空模型和手动动作队列。
机器人已连接时，重置后进入手动控制状态，运动使能（deadman）保持释放，需由操作员重新启用。
机器人尚未连接时，重置只解除启动时的停止锁定。

任务完成会调用适配器的保持/停止操作，但保持机器人
处于连接状态。服务关闭会断开连接。两种操作都不会规划返回
原点的轨迹。模型绑定只映射观测和动作；键盘/手柄
输入独立于这些绑定。机器人特定的轴到运动映射
位于 `robots/arx/x5` 和 `robots/lerobot/so101` 下。

## 按键与停止行为

- 键盘：空格停止，R 重置，Q 请求机器人保持当前位置并退出输入客户端。
- Linux 手柄：按钮 0 获取手动控制，按钮 1 停止，
  按钮 3 释放手动控制，按钮 4 是按住式 deadman；重置使用 R。
  在启用运动前，请在实际控制器上检查按钮编号。
- 手动心跳缺失 0.25 秒会释放 deadman，并请求机器人保持当前位置；
  输入结束（EOF）或输入错误也会触发该操作。执行失败会出现在
  `last_error` 中并锁存急停。

ARX5 和 SO101 将停止与当前 SDK 调用串行化；因此被阻塞的 SDK 调用
会延迟物理停止。FR3 显式允许并发停止。
软件停止不能替代硬件急停。使用所选机器人和手柄前，需验证按钮映射、
运动使能释放、模型控制接管、取消和停止延迟，并确认重置不会自动触发运动。
