# 相机采集与断连恢复实验

在负责相机采集和观测读取的环境中安装 `camera` 可选依赖即可，其他服务无需安装 OpenCV 或 Pillow。

`embodirun.services.rollout.camera_capture` 持续读取 V4L2 相机，按设定数量录制图像，
并为通信实验提供只读观测。它不连接机器人，也不提供运动接口；观测中的六个状态值使用固定测试数据。

## 启动采集服务

```bash
python -m embodirun.services.rollout.camera_capture \
  --camera front /dev/v4l/by-id/FRONT-video-index0 \
  --camera wrist /dev/v4l/by-id/WRIST-video-index0 \
  --output /tmp/so101-camera-run \
  --width 640 --height 480 --fps 30 \
  --record-count 120 --record-hz 2 --duration-s 600
```

将示例路径替换为实际相机别名，确认它们指向已注册的 `/dev/videoN` 设备，并使用新的输出目录。
进程会在达到设定时长后退出，也可通过 SIGTERM/SIGINT 停止；退出时释放设备。

服务默认监听 localhost:29480。`/health` 返回采集速率、计时、进程 CPU 时间和录制进度；
`/latest` 返回最近一组完整的相机 JPEG 和采集时间戳，仅在采集期间可用。
`/frame/INDEX` 按索引循环读取已录制序列。成对测量前，等待 `recorded` 达到
`record_count_target`，确保录制序列不再变化。读取实时帧时，还需检查帧是否过期。

要服务特定的实验节点，选择一个局域网 `--bind` 地址，并显式地
用 `--allow-host` 添加其 IP。没有 POST 或动作端点。在本地观测客户端中禁用代理
环境变量处理，以保持相机流量在本地。

## 录制与回放

`ReplaySource` 可读取 `observations.jsonl` 和 JPEG。`capture.jsonl` 记录采集负载，
`process.json` 和 `final.json` 保存进程及退出信息。
比较传输方式时，一边持续采集、一边回放相同的录制数据，可在模型输入不变的条件下测量采集负载的影响。
实时输入每次不同，单独测量，不参与要求输入指纹一致的配对比较。

`CameraObservationSource` 禁用代理，通过 HTTP 读取采集服务。
录制模式逐帧核对固定数据，每次观测都包含 HTTP 读取和 JPEG 解码，不使用内存缓存。
实时模式在收发双方共用主机时钟时检查帧的时效，并将不同运行的输入指纹标记为不一致。
跨主机的单调时间戳只保留为来源信息，不直接相减计算延迟。

## 采集负载对延迟的影响：2026-09-11

Orin NX 和 AGX Orin 共接入四路 SO101 相机，Thor 运行 Pi05 推理。
测试使用预设关节状态和零奖励，只在内存中校验动作。成对测试期间持续采集，
两种方案均通过 HTTP 读取相同的录制 JPEG，将两个视角解码并缩放为 224 × 224 RGB。
另用实时输入测量采集数据从生成到使用的时间。

五组正常 C/D 配对比较了 RLinf channel 传输与 EmbodiRun
wireless 端点，二者位于同一有线局域网。每台设备在每次试验中以 2 Hz 发送 100 个请求，超时设为一秒。
两种方案均收到 1000/1000 个有效响应。Wireless 将成对 RTT p95
平均降低 8.01%，成对 bootstrap 95% CI 为 [-10.14%, -5.42%]；试验 p95 均值
为 Channel 253.88 ms、Wireless 233.56 ms。这是在
所测负载下的延迟结果；有效吞吐相同。RTT 包含推理和排队。
另一项五对 A100–Thor 测试运行了真实的 PPO 更新和原生 CPU/Gloo patch
权重同步，并固定到特定的 RLinf 和 EmbodiRun 修订版本。加入 EmbodiRun
使稳态权重就绪 p95 平均变化 +12.28%，95% CI 为 [-8.03%, +32.16%]。
该宽区间同时包含更快和更慢的权重更新。平均
更新为 1.110 GB，其中 56.13% 在索引中。无损 16 位列索引打包
将节省约 249 MB/次更新（占负载的 22.45%），但尚未测得
优化后的硬件就绪时间改进。权重更新仍使用 RLinf 的 syncer；
切换观测传输不会替代该路径。

### 暂停进程后的恢复

三组配对测试均将 NX 进程暂停两秒。Channel 收到 282/300 个有效 NX 响应，
Wireless 收到 284/300 个；未受影响的 AGX 在两种方案下均收到 300/300 个有效响应。
六次试验都在恢复后继续处理新调度的请求，直到运行结束。
恢复后的首个有效响应耗时 C/D 1579/1525、1578/1457 和 1906/1089 ms。实际
暂停发生在受影响设备测量窗口的 5.36–5.53 秒处，具体落在请求周期中的哪个时刻会影响恢复耗时。
两种方案均从进程暂停中恢复。

### TCP 断连恢复

先对原有接收逻辑进行三组 TCP 故障配对测试：主动关闭受影响 worker 与 Thor 的数据连接，
保留 Ray 控制端口和相机端口。两种方案使用相同的 EmbodiRun 消息封装和动作校验。
Channel 关闭八个原生 data/store socket；Wireless 按相同的对端和端口规则，每次关闭一个 socket。
断开后允许重连，测试不包含持续断网或设备重启。

两个原始变体都未能恢复 NX 流：每个都接受了 30/300 个计划
NX 响应，且全部在故障之前，而健康 AGX 接受了 300/300 个。每个受影响的
试验启动了 11 次交换，其中十次成功、一次超时；其余 89 个时隙
被标记为中止并保留在分母中。每个变体在断开后
调度的 267 个时隙均未成功。硬件日志显示 Channel 出现 Gloo 连接错误，
而 Wireless 的各设备接收循环因 `ConnectionClosedError` 退出。
仅靠传输重连并未重启该接收任务。

另外三组配对启用了 `retry_disconnected_receive`。Channel 仍为
30/300 个受影响 NX 响应，没有恢复。Wireless 接受了 300/300 个受影响
NX 响应和 300/300 个健康 AGX 响应，没有错误或延迟/丢失的时隙。
关闭后调度的全部 267 个时隙都成功，每次试验都到达了最后一个
请求。关闭后的首个有效响应耗时 433、404 和 356 ms，包含
推理和请求节奏。严格意义上的首批关闭后调度时隙
在 937、910 和 834 ms 后完成；调度间隔为 500 ms。

该改进需要启用 `retry_disconnected_receive`，在断连后重新等待接收；该选项默认关闭。
它保留原有的绝对接收超时和严格的流
会话/序列检查，且从不重发负载。这些约五秒的
故障发生时没有未完成的请求，测试的是空闲连接恢复。

另外三组配对在 5.1514–5.1519 秒时关闭连接，且请求 10
在每次试验中都未完成。启用该选项后，Wireless 在每台设备上均收到 300/300 个有效响应，
包括全部 267 个新调度的关闭后时隙，并到达了每个最终请求。
Channel 仍只收到 30/300 个受影响设备的响应，未恢复；未受影响的设备
接受了 300/300 个。Wireless 的首个有效响应在 178、238 和 245 ms 后到达；
首批严格意义上的关闭后时隙在 684、726 和 740 ms 后完成。
未完成的请求可能已经到达 GPU。测试部分
消息丢失或中断的 PPO 轨迹需要不同的故障注入。

### 实时采集结果

单独的实时输入试验各自接受了 200/200 个响应。Channel/Wireless RTT
p95 为 254.36/251.36 ms，本地软件从采集开始到响应的 p95 为
478.23/463.08 ms。这不是传感器曝光时序，也不是相同输入的成对比较。
相机在 NX/AGX 上以 10.26/10.23 成对帧/秒采集了约 3.2 小时；
平均 CPU 为单核的 33.77%/34.13%。保存的 480 个 JPEG 通过了校验和检查。
Thor 完成了 42,817 次后台相机读取，没有错误。实验进程
已停止；来自另一个 Thor 工作区的常驻 HTTP 推理服务
被保留，因此 GPU 使用不保证独占，也不保证不受其他请求影响。
