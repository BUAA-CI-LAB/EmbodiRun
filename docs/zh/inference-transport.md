# HTTP 与 WirelessComm 推理延迟对比

EmbodiRun 的 HTTP 和 WirelessComm 使用同一套[推理协议](http_api.md)。
本实验比较两种传输在机器人节点上的端到端延迟，并拆分请求各阶段的耗时。
其他可选方案见[传输优化实验](transport-experiments.md)。

两种协议运行在同一段有线局域网上，且未配置带宽限制。

## 实验配置

计算节点运行带 SO101 适配器的 PI0.5 服务，AGX Orin 和 Orin NX 两个机器人节点各运行一个客户端。
每个客户端最多保留一个未完成请求，按文件顺序回放同一份输入列表。
每端先预热 20 个请求，再通过同步屏障同时开始计时，各发送 200 个正式请求，共 400 个。
本次服务配置为 B=1，两个客户端的请求需要排队，模型不会并行执行。

两个部署配置只在传输方式上不同。检查点、BF16、
10 步去噪、整环 CUDA graph 和 50×6 动作输出
完全相同。输入是录制的：相机 JPEG、关节状态和指令来自
机械臂，只有链路本身在接受测试。每种协议回放同一份
清单。SHA-256 覆盖指令、状态、相机名称、编码后的图像
字节和样本顺序，因此 `compare` 会拒绝输入不同的配对。
建议在各轮之间交替协议顺序；下面的 2026-09-08 运行
使用了 HTTP → WirelessComm → WirelessComm → HTTP。

该基准测试使用回放的观测来测量推理请求和动作校验；
它不执行机器人运动。

## 测量指标

| 指标 | 定义 |
|---|---|
| E2E mean / P50 / P95 / P99 (ms) | 从机器人节点上构造请求，到接收响应并完成 SO101 动作映射和 50 行校验。 |
| RPC (ms) | `client.step`：请求序列化、传输、服务排队、预处理、模型执行、后处理和响应解析。 |
| calls/s per end | 该端的成功请求数除以该端的正式测量时间。 |
| aggregate calls/s | 两端的成功请求数除以主机开始信号与两个完成信号之间的时间间隔。 |
| 失败 | 失败的尝试及其持续时间会被保留；该端在首次失败时停止且不重试，该轮被标记为失败。 |

E2E 不计文件读取、SSH 输入分发、预热、连接和会话建立、传感器采集及机械臂运动。
各端使用本机单调时钟测量延迟，无需跨设备同步时钟；聚合吞吐的计时包含少量 SSH 启停信号开销。
`server_timing_ms` 记录服务端耗时。预热与正式请求均使用不同 ID，不会复用幂等缓存中的结果。

测量完成后，两端先关闭各自的服务会话，再释放传输连接。
若会话关闭失败，仍保留测量结果，但将该轮标记为失败。
测试只调用推理客户端和动作映射器，不打开串口或相机，也不执行动作。

## 端到端延迟：2026-09-07

两个 SO101 机械臂各记录了 24 个观测——48 组、96 张 JPEG——且每个
电机的标定寄存器都与其文件匹配。全部四路相机画面
几乎全黑：超过 99.5% 的像素低于 16/255，只有
少数指示灯在前视图中可见。一组中的两张 JPEG
在 AGX Orin 上平均为 11,106 字节，在 Orin NX 上为 12,164 字节。下面的
测量使用这些体积小、画面暗的负载。

两种协议均完成 400 个正式请求，返回 50×6 动作，会话正常关闭。
下表每行对应预热 20 个请求后的一轮测量：

| 协议 | 客户端 | 调用数 | E2E mean (ms) | P50 (ms) | P95 (ms) | P99 (ms) |
|---|---|---:|---:|---:|---:|---:|
| HTTP | AGX Orin | 200 | 434.81 | 435.05 | 443.28 | 444.04 |
| HTTP | Orin NX | 200 | 433.74 | 435.88 | 442.60 | 444.54 |
| WirelessComm | AGX Orin | 200 | 419.31 | 421.62 | 425.42 | 426.87 |
| WirelessComm | Orin NX | 200 | 420.34 | 421.63 | 425.32 | 426.92 |

聚合吞吐在 HTTP 下为 4.595 calls/s，在 WirelessComm 下为
4.755 calls/s。

每个机械臂的第一个观测还与真实的 PI0.5
输出进行了比对：两者都返回了 50×6 的有限值。第一个预测目标与
当前位姿的偏差在关节上最高约为 113.0° 和 56.2°，在夹爪上为 21.5
和 15.5，全部超过配置的每步限制。没有将任何模型动作
发送给电机。

## 各阶段耗时：2026-09-08

第二次运行只加载一次模型，并由该进程同时服务两种传输，
因此各协议分支复用同一个处理器和 CUDA graph。两个机器人节点
都通过有线局域网访问计算节点。只回放了此前录制的观测；
没有打开串口，也没有执行任何动作。单客户端
HTTP 和 WirelessComm 各进行 50 个正式请求，随后双客户端运行
按 HTTP → WirelessComm → WirelessComm → HTTP 的顺序每端进行 100 个。全部 900 个
正式请求都以 50×6 动作成功完成。

| 场景 | HTTP E2E mean | WirelessComm E2E mean | E2E 降幅 | Aggregate calls/s | 吞吐提升 |
|---|---:|---:|---:|---:|---:|
| AGX Orin，单客户端 | 217.25 ms | 207.13 ms | 4.65% | 4.586 / 4.811 | 4.91% |
| AGX Orin + Orin NX，两轮合并 | 437.03 ms | 418.12 ms | 4.33% | 4.560 / 4.765 | 4.49% |

双客户端各轮的平均值分别为 HTTP 的 437.82 / 436.23 ms 和
WirelessComm 的 416.47 / 419.76 ms。合并 P95 为 442.37 / 421.92 ms，合并
P99 为 443.85 / 423.12 ms。单客户端场景只有一轮；每个
双客户端协议有两轮。

同一次运行还记录了各阶段耗时。下表为双客户端场景下每个请求的平均值，
各阶段互不重叠，相加即为 E2E；差值为正表示 WirelessComm 在该阶段耗时更短。

| 阶段 | HTTP (ms) | WirelessComm (ms) | HTTP − WirelessComm (ms) |
|---|---:|---:|---:|
| 客户端请求与动作映射 | 0.63 | 0.64 | −0.01 |
| RPC 周边：网络、协议编解码、服务路由 | 7.89 | 6.17 | 1.72 |
| 等待共享推理锁 | 208.41 | 200.92 | 7.49 |
| 输入准备：状态、图像、处理器 | 13.32 | 10.11 | 3.21 |
| 引擎调用，包括同步和动作复制到 CPU | 203.43 | 197.58 | 5.85 |
| 动作后处理、适配器、其余服务计时 | 3.34 | 2.69 | 0.65 |
| **E2E** | **437.03** | **418.12** | **18.91** |

在输入准备内部，图像解码和张量构建耗时 10.41 / 7.53
ms。引擎已有的 CUDA 事件分为 92.77 / 89.91 ms 的 prefill 和
10 步去噪的 109.91 / 107.40 ms。这些流时间已经
包含在引擎调用内，不再重复计入。

| 计时字段 | 含义 |
|---|---|
| `profile_lock_wait_ms` | 等待共享 PI0.5 推理锁的墙钟时间。 |
| `profile_state_ms` / `profile_images_ms` | 状态转换，以及 JPEG 解码和图像张量构建。 |
| `profile_prepare_ms` | 模型输入处理器。 |
| `profile_engine_wall_ms` | 整个 `EngineCore.execute` 调用，包括其同步和动作复制回 CPU。 |
| `profile_core_prefill_ms` / `profile_core_decode_ms` | 引擎已有的用于前缀阶段和去噪阶段的 CUDA 事件。是流时间，而非各内核耗时之和。 |
| `profile_core_e2e_ms` | 引擎已有的墙钟计时，在动作被打包之前结束。 |
| `profile_restore_ms` | 动作反归一化及类似后处理。 |
| `profile_adapter_other_ms` | 其余适配器工作：动作检查、列表转换和探针开销。 |

CUDA 分段计时已包含在引擎总耗时中，只用于诊断，不能再次加到 E2E 上。
只有互不重叠的墙钟计时阶段才能相加；不同进程的绝对时钟也不能直接相减来计算单向网络延迟。
这些字段随诊断响应返回，性能分析输出与原始基准测试报告分开保存。

## 主要结论

- 在该负载下，WirelessComm 带来约 **4.5% 的总吞吐提升**。一次
  独立启动模型服务的更早运行测得 3.47%。
- 在 **18.91 ms** 的 E2E 降幅中，**1.72 ms** 来自通信和 RPC
  处理；其余来自排队、预处理和模型执行。
- 在两个客户端下，引擎调用加锁等待占 E2E 的 **94–95%**，而
  单客户端锁等待低于 0.001 ms。客户端数量翻倍后
  聚合吞吐仍接近 4.6–4.8 calls/s，而每端的
  延迟大约翻倍，因此瓶颈是串行化 B=1 服务下的
  模型处理及其排队。
- 即使只加载一个模型，两个入口的预处理和 CUDA 流时间
  也不同，这意味着独立加载模型并不是方差的唯一
  来源。

## 差异来源与复测建议

HTTP 客户端使用 `urllib.request.urlopen`，它在每个请求上发送 `Connection: close`，
而服务器的每个连接都由自己的
线程来服务。WirelessComm 通过线程池复用连接。线程复用、
调度和设备时钟都可能影响服务内部计时，且没有
进行线程复用消融实验，也没有记录每个请求的时钟，因此
线程复用和设备时钟变化的影响仍未确定。

要比较协议本身，请增加一个 HTTP 连接复用分支，使线程复用条件
更接近，然后重复分段测量。

对于你的部署，请用有代表性的图像、负载
大小和网络条件重复该对比。这些运行在有线局域网上每个请求
大约使用 11.6 kB 的 JPEG 数据。
